# mfc2_EA-EM_TDR

EA-EM pipeline: ensemble EM (ECa) inversion + TDR-calibrated Waxman-Smits petrophysics → soil water content. Works on synthetic scenarios and on real MFC2 field data.

Outputs go to `mfc2_outputs/<scenario output_dir>/<NNNN>_<scenario>/`; every run is appended to `mfc2_outputs/run_log.csv`.

## Installation

Requires Python >= 3.12 (results were produced with 3.12). The repository is a set of scripts, not an installable package: clone it, install the dependencies, and run everything from the repository root.

```bash
git clone https://github.com/BenjMy/mfc2_EA-EM_TDR
cd mfc2_EA-EM_TDR
```

With conda:

```bash
conda env create -f environment.yml
conda activate eaem
```

Or with pip / venv:

```bash
python3.12 -m venv ~/venvs/eaem
source ~/venvs/eaem/bin/activate
pip install -e ".[dev]"
```

Dependencies: `numpy`, `scipy`, `pandas`, `matplotlib`, `tqdm`, `emagpy` (`pytest` for the tests). Check the install with `pytest tests` and `./run_one_scenario.sh --list`. The launchers are bash scripts; on Windows use WSL or Git Bash. Numerical results can differ slightly between Python/library versions, so compare runs only within one environment.

## Which data? Real, synthetic mirror, or in-process synthetic

Three kinds of input go through the same pipeline. Short copy-paste version: [`RUNNING.md`](RUNNING.md).

| Kind | Scenarios file | What it is |
|---|---|---|
| **real** | `ensemble_scenarios_real.json` | The MFC2 field data in `./data/` (see "Input data paths"). |
| **synthetic mirror** | `mfc2_synthetic/mfc2_real_synthetic_mirror.json` | A synthetic twin of the field deployment (same 7 EM dates and point-count asymmetry, same TDR depths, known truth), written as files by `generate_synthetic_real_mirror.py` and read by the real-data loader. |
| **in-process synthetic** | `ensemble_scenarios.json` | Synthetic scenarios generated inside the run (`2d`, `1d_surface_tdr`, ...). |

The hypothesis scripts (`run_all_hypotheses.py`, `hyp1_*`, `hyp2_*`, `hyp3_*`) choose between the first two with one switch, **`--data real`** (default) or **`--data synthetic`**. It sets `--config` and `--base`, and synthetic results go to `mfc2_outputs/hypotheses_synthetic/` so they never overwrite the real ones (`--config <mirror json>` without `--data` is detected as synthetic). The plan printed by `--dry-run` has a `DATA:` line with the EM / TDR / coordinate paths and says `REAL FIELD DATA` or `SYNTHETIC MIRROR`.

Caveat: the mirror is read through the real-data loader (`"data_source": "real"` in its JSON), so the banner of `run_one_scenario.sh` says `REAL DATA` for it as well. In that launcher, check the `EM=` path (`./data/EMI_MFC2/` = real, `mfc2_synthetic/EMI_MFC2_synthetic` = mirror).

## Run one scenario

```bash
./run_one_scenario.sh --list                          # list scenarios
./run_one_scenario.sh --validate                      # validate ensemble_scenarios.json
./run_one_scenario.sh -s 1d_surface_tdr --mode 1d --num-swc-positions 5   # synthetic, 1-D transect
./run_one_scenario.sh -s 2d --mode 2d                 # synthetic, 2-D grid
./run_one_scenario.sh --mode 2d -s real_single_base -c ensemble_scenarios_real.json   # real data (paths set in the JSON)
./run_one_scenario.sh --mode 2d -s mfc2_real_synthetic_mirror \
    -c mfc2_synthetic/mfc2_real_synthetic_mirror.json     # synthetic mirror of the real data (known truth)
python run_all_hypotheses.py --data real --fast --dry-run        # the three hypothesis tests on the real data, plan only
python run_all_hypotheses.py --data synthetic --fast --dry-run   # the same on the synthetic mirror
./run_one_scenario.sh --help                          # all options
```

Scenarios are defined in `ensemble_scenarios.json` (synthetic) and `ensemble_scenarios_real.json` (real). A scenario can start from another one with `"extends": "<name>"` (nested objects are merged, lists/scalars replaced); `ws_layer_params` sets per-layer true Waxman-Smits parameters for synthetic data. The surface-vs-full study families `1d_{surface,full}_free{K}` and `1d_{surface,full}_hetero_free{K}` are generated by `sweeps.py` from the two base scenarios `1d_surface_tdr` / `1d_full_depth_ref` (they are not in the JSON; an entry of the same name in the JSON would override the generated one). `python scenario_loader.py --list-scenarios` lists everything, generated names included.

Tests: `pytest tests`.

## Command-line recipes (real data)

Copy-paste starting points, all run from the repository root. Scenario `real_L3_base` (3 layers, `a` and `m` fixed, `sigma_w` and `sigma_s` free) is used as the example; swap in any scenario of `ensemble_scenarios_real.json`. The options are explained in the sections below and in `./run_one_scenario.sh --help`.

### 1. Check before you compute

```bash
./run_one_scenario.sh --list                          # scenarios available
./run_one_scenario.sh --validate                      # is the scenario JSON consistent?
python EA_EM_config.py --check                        # do the input data paths exist?
python hyp1_layers_ws_freedom.py --designs L3 --free-k 4 --dry-run   # plan only, nothing runs
```

### 2. The standard workflow: calibrate, then map

Calibration is run first on the probe neighbourhoods (cheap relative to a full map); the map stage then inverts all EM points, only for the ensemble members selected by the calibration.

```bash
# a) calibrate (Steps 0-5, stops before the map)
./run_one_scenario.sh -s real_L3_base -c ensemble_scenarios_real.json --mode 2d --stage calibrate

# b) find the calibrate folder of that run (column output_dir of the run log)
tail -n 3 mfc2_outputs/run_log.csv | cut -d, -f1,3,6,7

# c) map, pointing at that folder (or at its stage_calibration.json)
./run_one_scenario.sh -s real_L3_base -c ensemble_scenarios_real.json --mode 2d --stage map \
    --calibration mfc2_outputs/real_L3_base/0001_real_L3_base_calibrate
```

Check the quality gate (`status`, `quality_reasons`) in the run's `run_manifest.json` and in `pipeline_report_*.md` before mapping. If the map run prints `[WARN] CALIBRATION DRIFT`, the map no longer matches the calibration: redo step (a). `--stage map` cannot be combined with `--quick`.

### 2b. Faster inversion: solver, cores and the progress line (`--em-method`, `--em-njobs`)

Step 1 (the EM inversion) is the long part. Two switches speed it up, and one line tells you how long it will take.

**Solver, `--em-method`.** The default is now **L-BFGS-B** everywhere (the scenario files carry it; ROPE did not fit the data, see "EM inversion method and speed"). L-BFGS-B is faster than ROPE only with **fixed depths**, so the synthetic SWC study defaults to `lbfgsbfix` (L-BFGS-B with the interfaces fixed at the truth) while the real-data scripts keep each scenario's own depth mode (all `real_*` scenarios are fixed-depth except `*_depth_free`).

| Value | Method | Depths | Default of |
|---|---|---|---|
| `lbfgsb` | L-BFGS-B | the scenario's own | hyp1/2/3, `run_all_hypotheses.py`, `run_real_study.py`, `generate_synthetic_real_mirror.py` |
| `lbfgsbfix` | L-BFGS-B | fixed (at the scenario's `depths0`) | `study_swc_design.py` |
| `rope` | ROPE (random sampler, optional, the old behaviour) | the scenario's own | none |
| `base` | untouched: whatever the scenario file says (L-BFGS-B now) | untouched | none (no name / cache suffix) |

**Cores, `--em-njobs {auto,N}`.** Splits the points of ONE Step-1 task across cores. `auto` (default) does it only when there are fewer tasks than cores (typically `--stage map`: K members x epochs); it is 1 for ROPE (seeded, reproducible) and with `beta != 0`, and it does not change a deterministic result. The launcher `run_one_scenario.sh` forwards it (and `--no-eta-benchmark`) to `run_pipeline.py`; scripts that call the launcher (`hyp*`, `run_all_hypotheses.py`, `run_real_study.py`, `study_swc_design.py`) pass it after a bare `--`.

| You run | Solver | Cores |
|---|---|---|
| one scenario / `--stage calibrate` / `--stage map` | edit nothing (file is L-BFGS-B); `-c <derived file>` for `rope` | `./run_one_scenario.sh ... --em-njobs 8` |
| `hyp1/2/3`, `run_real_study.py`, `run_all_hypotheses.py` | `--em-method lbfgsb` (default) \| `rope` \| `base` | `... -- --em-njobs 8` |
| `study_swc_design.py` | `--em-method lbfgsbfix` (default) \| `lbfgsb` \| `rope` \| several (a factor) | `... -- --em-njobs 8` |

```bash
# real data, calibrate then map (map has few tasks: the cores go inside each task)
./run_one_scenario.sh -s real_L3_base --mode 2d --stage calibrate
./run_one_scenario.sh -s real_L3_base --mode 2d --stage map --em-njobs 8 \
    --calibration mfc2_outputs/real_L3_base/0001_real_L3_base_calibrate
python hyp1_layers_ws_freedom.py --designs L3 --free-k 4 -- --em-njobs 8          # solver already lbfgsb
python em_options.py --config ensemble_scenarios_real.json --em-method rope       # -> ..._rope.json, the old solver
```

Use the SAME scenarios file (same method and depth mode) for calibrate and map: the map looks the calibrated members up by method and stops if they are missing. A non-`base` `--em-method` appends `_<em>` to `cache_tag` and `output_dir` of the derived scenarios, so two solvers never share a cache or a run folder.

**Progress and time left (Step 1).** Before dispatch the pipeline times about 3 points of each (method, forward model) in the main process and prints an estimate: `[ETA] Step 1 | calibrate estimate: about 42 min 10 s on 8 worker(s), finishing around 14:35` (rough, +-50 %; `--no-eta-benchmark` skips it). Then ONE live line replaces the old per-worker output: percent, tasks, points, elapsed, ETA with the clock time, workers and points/s. The ETA follows points, not tasks (tasks differ a lot in size) and blends the recent rate in, so a stall shows. On a terminal it refreshes in place; in a log file (nohup, batch) it prints one line every 30 s. EMagPy's `n/N inverted` and quadrature-conversion messages are filtered out of the workers' output; anything else they print is kept.

**Threads per worker.** The pool runs one process per core, so each worker is limited to one BLAS / OpenMP thread (`OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`, ... are set to 1 for the workers; the run prints a line saying so). Without this, 24 workers each starting 24 BLAS threads oversubscribe the machine: a calibrate run of 532 k points went from 39 to 215 pts/s (ETA 3 h 48 min to 41 min) with the limit. A value you exported yourself is never overwritten (a value > 1 prints a `[WARN]`). If the live rate later falls below a quarter of the benchmark's expected rate (after 60 s), one `[WARN]` line suggests the usual causes: threads, other jobs on the machine, fewer physical cores than workers.

### 3. Free more Waxman-Smits parameters

`real_L3_base` fixes `a` and `m`. To free them, do not edit the JSON by hand: the `hyp1` script generates the scenario `real_study_<design>_free<K>` (K = number of free parameters, freed in the order `sigma_s`, `m`, `sigma_w`, `a`).

```bash
python hyp1_layers_ws_freedom.py --designs L3 --free-k 4 --stage both          # 4 free, calibrate then map
python hyp1_layers_ws_freedom.py --designs L3 --free-k 2 4 --stage calibrate   # compare 2 vs 4 free (calibration only)
python hyp1_layers_ws_freedom.py --design L3b=0.2,0.5 --designs L3b --free-k 2 # your own layer depths (m)
```

Step 1 (the ensemble inversion) does not depend on the WS freedom, so all K of one design share a single cache and the expensive part is computed once. `--stage both` skips the map of a scenario whose calibration failed. With 4 free parameters and only about 20 probes, `a`, `m` and `sigma_s` can compensate each other: judge the result on held-out data (next recipe), not on the training RMSE.

### 4. Validate on held-out data

```bash
# one run with whole probes held out
./run_one_scenario.sh -s real_L3_base -c ensemble_scenarios_real.json --mode 2d \
    --stage calibrate --train-val-split by_probe

# the same scenario with every split method; summary in hyp2_summary.csv
python hyp2_train_val_split.py --base real_L3_base
python hyp2_train_val_split.py --base real_L3_base --methods off by_probe   # only some methods

# the same split on the hyp1 scenarios (anything after a bare -- goes to run_one_scenario.sh)
python hyp1_layers_ws_freedom.py --designs L3 --free-k 2 4 -- --train-val-split by_probe
```

The flag takes two dashes and one of `alternate_sorted`, `by_probe`, `by_time_block`, `random` (`by_probe` is the only one that is independent in space). The held-out scores are the `val_rmse_pct` and `val_rsr` columns of `mfc2_outputs/run_log.csv`.

### 5. Localized Waxman-Smits and the bandwidth

```bash
# let the leave-one-probe-out CV choose among your own candidates (in m)
./run_one_scenario.sh -s real_L3_base -c ensemble_scenarios_real.json --mode 2d --stage calibrate \
    --ws-localized-bandwidth-sweep 3 5 8 12 20 30 40

# fix the bandwidth (overrides the value stored by calibrate when used with --stage map)
./run_one_scenario.sh -s real_L3_base -c ensemble_scenarios_real.json --mode 2d --stage map \
    --calibration mfc2_outputs/real_L3_base/0001_real_L3_base_calibrate --ws-localized-bandwidth 12

# maps with ONE parameter set per horizon instead (the previous behaviour)
./run_one_scenario.sh -s real_L3_base -c ensemble_scenarios_real.json --mode 2d --stage map \
    --calibration mfc2_outputs/real_L3_base/0001_real_L3_base_calibrate --ws-map-calibration global

# the bandwidth hypothesis on its own
python hyp3_localized_bandwidth.py --base real_L3_base --bandwidths 3 5 8 12 20 30 40
```

If the chosen bandwidth is the largest candidate of the sweep (for the MFC2 run of 2026-11-23 it was 20 m), the optimum may lie beyond it: extend the list. The stations are 20-32 m apart, so below about 20 m a sweep cannot show much.

### Common mistakes

| Symptom | Cause / fix |
|---|---|
| `unrecognized arguments: -train-val-split by_prob` | One dash instead of two, and `by_prob` instead of `by_probe`: `--train-val-split by_probe`. |
| Map stage asks for `--calibration` or stops at the first step | `--stage map` needs the calibrate folder (or its `stage_calibration.json`) of the same scenario. |
| `[WARN] CALIBRATION DRIFT` | `depths0`, `cond_ranges`, epochs or the WS freedom changed since calibrate: redo `--stage calibrate`. |
| A scenario has `a` and `m` fixed but you want them free | Use `hyp1_layers_ws_freedom.py --free-k 4` (recipe 3); `ws_fixed_params`: `true` = fixed, `false` = free. |
| `Import openpyxl failed` | Install it in the environment: `pip install openpyxl`. |
| Quality gate `WARN`: uncalibrated horizon | A horizon without a TDR sensor keeps the prior WS parameters (`lab_p0`); expected for H2 of `real_L3_base`. |
| Map covers only the probe neighbourhoods | The scenario already thins with `em_subsample.mode = "probes"` (e.g. `real_single_test_probes*`): map with a scenario without it. |
| `--stage map` with `--quick` is rejected | Not supported: run the map without `--quick`. |
| Map stops: calibrated member(s) not in this scenario's parameter grid | The map uses another scenarios file / EM method than the calibration (e.g. ROPE vs `..._lbfgsb.json`): use the same one for both stages. |
| L-BFGS-B is slower than ROPE | Free depths (`fixed_depths: false`; all synthetic scenarios, `real_*_depth_free`): L-BFGS-B is 2-7 x slower than ROPE there. Use fixed depths (`--em-method lbfgsbfix`, the study default). |
| Step 1 runs far slower than the `[ETA]` estimate (a few pts/s per worker) | Thread oversubscription: the pipeline now limits workers to one thread, unless your shell exports `OMP_NUM_THREADS` / `OPENBLAS_NUM_THREADS` / `MKL_NUM_THREADS` > 1 (`unset` them or set them to 1). Also check other jobs and the number of physical cores. |
| `--em-njobs` does nothing | `auto` keeps 1 when the tasks fill the cores (a full calibrate, the SWC study), for ROPE and with `beta != 0`. It helps `--stage map` and runs with few tasks. |
| `--em-njobs` is rejected by a `hyp*` / study script | Those scripts forward it only after a bare `--`: `python hyp3_localized_bandwidth.py ... -- --em-njobs 8`. |

## Input data paths (`EA_EM_config.py`)

All input paths of the real-data branch live in `EA_EM_config.py`, grouped as a named *dataset* (`em_dir`, `tdr_dir`, `coord_file`). `mfc2` is the built-in default, so existing runs are unchanged. To use another site, add a dataset (edit `DATASETS`, or put it in `EA_EM_datasets.json` next to the file) and select it:

```bash
python EA_EM_config.py --list                 # known datasets
python EA_EM_config.py --dataset my_site --check   # do the paths exist?
./run_one_scenario.sh --mode 2d -s real_single_base -c ensemble_scenarios_real.json --dataset my_site
EA_EM_DATASET=my_site ./run_one_scenario.sh ...    # same, through the environment
```

Precedence: explicit `--em-dir/--tdr-dir/--coord-file` > `--dataset` > paths written in the scenario JSON > `$EA_EM_DATASET` > `mfc2`. A real-data scenario may omit `em_data_dir`/`tdr_data_dir`/`coord_file` and take them from the dataset. `EA_EM_DATA_ROOT` relocates the default `./data` tree.

## Calibration options (real data)

What is calibrated, and over which units, is set **per scenario** in `ensemble_scenarios_real.json` (fields are inherited with `"extends"`); the input data come from `EA_EM_config.py` (see above). The Waxman-Smits (WS) parameters are `a`, `m`, `sigma_w`, `sigma_s`; horizons come from `depths0` and the probe depths (the real TDR sensors sit at 0.15 and 0.30 m).

| Calibration unit | Status | Where to set it |
|---|---|---|
| **One parameter set per horizon, pooled over all stations** | Used by Steps 2, 4, 5 (ranking, K, RMSE) and, with `--ws-map-calibration global`, by the maps. | `ws_fixed_params` (`true` = fixed, `false` = free; freed in the order `sigma_s`, `m`, `sigma_w`, `a` by the `hyp1` scenarios), `lab_p0` (start / fixed values), `ws_bounds` (default `a` 0.5-5, `m` 1-4, `sigma_w` 1-1000, `sigma_s` 0-200), `depths0` + `cond_ranges` (layers) |
| **Per EM point, kernel-weighted by the distance to the stations** (Gaspari-Cohn) | **Default for the maps** (`--ws-map-calibration localized`, see below), bandwidth chosen by leave-one-probe-out CV; also drawn in `petro_calibration_localized*.png`. Steps 2-5 (ranking, K, RMSE) still use the global fit. | `ws_localized_bandwidth` or `ws_localized_bandwidth_sweep` in the scenario, or `--ws-localized-bandwidth[-sweep]`. The bandwidth is in metres: use values of the order of the station spacing (the MFC2 stations are 20-32 m apart, so a sweep below about 20 m cannot show anything) |
| **Per station** | Not available in Step 5 / maps (see `to-do.md`). | - |
| **Per zone (cluster of stations)** | Not available (see `to-do.md`). | - |

**Train / validation split** (`train_val_split`, or `hyp2_train_val_split.py`): this is a way to *validate* the calibration, not another calibration unit. The training part drives the WS fit **and** the choice of K; the validation part is held out and used once at the end to report an unbiased RMSE (Loiseau et al., 2026, Sec. 2.3 and 2.6). It can be done **by sensor**: `by_probe` holds out whole stations (fully independent, needs real probe ids, so real data only). The other methods are `off`, `alternate_sorted` (every other observation by sorted theta: not independent, the same probe or time step can be in both parts), `by_time_block` and `random`. With `off` the reported RMSE is in-sample and optimistic (0.092 vs a leave-one-probe-out 0.112 in the first real run).

## Running several real-data scenarios

The launchers form three levels. Each level only calls the one below it, and only `run_one_scenario.sh` does the computing:

```
run_all_hypotheses.py            ONE entry point: runs the hypothesis scripts below in turn
 |-- hyp1_layers_ws_freedom.py      H1  how many layers / how many free WS parameters
 |-- hyp2_train_val_split.py        H2  is the calibration good on held-out data
 `-- hyp3_localized_bandwidth.py    H3  does a localized WS calibration help, which bandwidth
       (each generates its scenarios with hyp_common.py, then calls the level below)
run_one_scenario.sh              ONE run of ONE scenario  ->  run_pipeline.py
run_real_all_scenarios.sh        fixed batch of run_one_scenario.sh calls (paper comparisons)
```

| Script | Question / role | Scenarios it uses |
|---|---|---|
| `run_one_scenario.sh` | One run of one scenario: `-s <name> -c <json>`. | Any scenario of the JSON you pass. |
| `hyp1_layers_ws_freedom.py` | **H1**: how many layers can the real TDR sensors support (they sit at 0.15 and 0.30 m), and how many Waxman-Smits parameters (sigma_s, m, sigma_w, a) can be freed? Layer designs `L2`/`L3`/`L4` (or `--design NAME=d1,d2`) x K free parameters. Prints which horizons have no sensor before running. | Generated `real_study_<design>_free<K>`. |
| `hyp2_train_val_split.py` | **H2**: the default run fits and selects K on all TDR data, so its RMSE is in-sample. Runs the same scenario with each split (`off`, `alternate_sorted`, `by_probe`, `by_time_block`, `random`) and reports the held-out RMSE. | Generated `real_tv_<method>` (from `--base`). |
| `hyp3_localized_bandwidth.py` | **H3**: does letting WS parameters vary in space (kernel-localized fit) beat one set per horizon, and at which bandwidth? Runs one scenario with your candidate list (`--bandwidths`), chosen by leave-one-probe-out CV. | Generated `real_bw_sweep` (from `--base`). |
| `hyp_common.py` | Not run directly: the shared engine of the three `hyp*` scripts (generate scenarios, write `<hyp>_scenarios.json`, print the plan, run `run_one_scenario.sh` per scenario, collect `<hyp>_summary.csv`). Defines the options they all share: `--data --config --base --mode --stage --out-dir --em-method --fast --dry-run --keep-going` (hyp2 / hyp3 and `run_all_hypotheses.py` also `--no-k0`), and forwards anything after a bare `--` (e.g. `--em-njobs 8`) to `run_one_scenario.sh`. | None (it generates nothing itself). |
| `run_all_hypotheses.py` | All of the above with their shared options (`--data --config --base --mode --stage --fast --dry-run --keep-going`); `--only 1 3` picks some, `--list` shows them. | Whatever the three scripts generate. |
| `run_real_all_scenarios.sh` | The fixed paper batch: `real_single_*` / `real_multi_*` (forward model `_base` / `_fslin` / `_cs`, fixed vs free interfaces `_depth_free`, WS freedom `_ws_*`), then `--beta`, `--gamma` and bandwidth sweeps and (commented out) `--train-val-split`. It starts with `--list` and `--validate`. Does not generate anything. | The existing `real_single_*` (2 layers) and `real_multi_*` (4 layers). |

The hypothesis scripts run `--stage calibrate` by default (probe neighbourhoods only, Steps 0-5), because all three are about the calibration quality; `--stage none` does the full run; `--stage both` runs, for every scenario, `--stage calibrate` and then `--stage map --calibration <that calibrate run folder>` (Step 6 on all EM points, inverting only the K selected members). If a calibrate run fails its map is skipped; with `--fast` the map is skipped too, because `--stage map` cannot be combined with `--quick`. The summary CSV has a `stage` column (one row per scenario and stage). `both` maps every scenario, which is expensive for exploratory variants you will discard (e.g. `L3`/`L4` horizons without a sensor): use `calibrate` to compare, then `both` on the chosen scenario. Each writes `<out-dir>/<hyp>_scenarios.json` (the generated scenarios; your JSON is not edited) and `<out-dir>/<hyp>_summary.csv` (final RMSE, CV score, ensemble size, runtime per scenario), under `mfc2_outputs/hypotheses/<hypothesis>/`. Step 1, the expensive ensemble inversion, is shared between the variants of one hypothesis. To add a hypothesis, copy `hyp3_localized_bandwidth.py`, change its question and scenario generator and register it in `run_all_hypotheses.py`. None of this has been run on the real data yet (see `run_paper_real.md`, a cheapest-first check that the dataset works with the pipeline).

```bash

The truth values are saved as `ground_truth/*_ws_sigma_s.npy` (EM points x layers, TDR stations x layers). The calibration's `sigma_s` bounds are [0, 200].
- Truth arrays are in `<outdir>/ground_truth/`; they are never read by the pipeline.
- **Truth maps during the run.** The generated / committed mirror JSON carries `"ground_truth_dir": "mfc2_synthetic/ground_truth"` (scenario key, optional, real-data mode). The grid is evaluated with the generator's own functions and checked against the saved `ground_truth/*.npy` (the log line `[truth] ... max |diff|` must be ~0).
- **Stand-alone** (no run needed): `python plot_synthetic_truth.py` writes the same three figures to `mfc2_synthetic/truth_plots/`; `--epochs 1 4 6` picks surveys, `--y <northing>` and `--zmax` set the xz section. Code: `plots/synthetic_truth.py`.

## Number / distribution of SWC probes study (1-D synthetic)

`study_swc_design.py` generates the scenarios, runs them, scores `theta_calc` against the synthetic truth and draws the comparison figures. Factors: number of SWC positions `n` (1, 2, 3, 5, 10), their distribution (`spread` / `clustered` / `random`), truth soil moisture (`smc` homo / hetero), truth Waxman-Smits parameters (`ws` homo / hetero), number of free WS parameters `K` (0-4, **K = 0 included by default**; 0 = all four known, the floor), the EMagPy regularisation (`noreg` / `beta` / `gamma` / `both`), what is known (`pin`) with an error on it (`err`), and the EM inversion method (`em`: `lbfgsbfix` by default / `lbfgsb` / `rope` / `base`, see 2b and "EM inversion method and speed"). `ws` also has the opt-in lateral / depth cases `heterox` / `heteroz` and their soil-like versions `soilhomo` / `soilheterox` / `soilheteroz` (baseline a, m, sigma_w, sigma_s = 0.8, 2, 100, 100 instead of 0.5, 3, 500, 100).

```bash
python study_swc_design.py --dry-run                      # write + validate the scenarios, print the commands
python study_swc_design.py --preset smoke --fast          # smoke test of the whole chain (8 short runs)
python study_swc_design.py --preset oat                   # one factor at a time around the reference (16 runs)
python study_swc_design.py --preset main --keep-going --resume   # truth x K x n, + distribution and reg at n = 5 (176 runs)
python study_swc_design.py --analyze-only                 # redo summary + figures from the run log
python study_swc_design.py --smc homo hetero --ws hetero --free-k 2 4 --n-swc 1 3 5 10   # any subset of the levels
# K = 0 floor only, legacy and soil truth (solver: lbfgsbfix, the default)
python study_swc_design.py --smc hetero --ws homo soilhomo --reg noreg --free-k 0 --n-swc 5 --dist spread \
    --resume --keep-going
# faster: L-BFGS-B with fixed depths + 8 cores per Step-1 task (anything after -- goes to run_one_scenario.sh)
python study_swc_design.py --preset main --resume --keep-going --em-method lbfgsbfix -- --em-njobs 8
# compare solvers as a factor (the old ROPE next to the default); every level doubles the runs
python study_swc_design.py --preset oat --em-method lbfgsbfix rope
python study_swc_design.py --preset oat --em-method lbfgsb      # L-BFGS-B with the base scenario's FREE depths: 4-7 x slower
```

Solver and speed of the study: the synthetic base scenarios have free depths, so plain `lbfgsb` is the slow variant; the default `lbfgsbfix` pins the interfaces at the truth layers (removes the depth question from the WS study on purpose; about 1.4 s against 11 s per Step-1 task in a quick run). Each run is one pipeline call with its own process pool (one worker per core, at most one per task), so `--em-njobs` only matters when a run has fewer tasks than cores. Runs made before the default changed were ROPE and carry no `_em` suffix (`base` in the log): `base` now means the scenario file's own method, which is L-BFGS-B, so use `--em-method rope` to repeat them.

Presets: `smoke` 8, `oat` 16, `main` 176, `full` 720 runs (K = 0 counts once per truth and regularisation, at the smallest `n`: it fits nothing, so it does not depend on `n` or the distribution). A synthetic run always repeats Step 1 (the ensemble cache is real-data only), so each run costs a full pipeline run (3-5 min; `--fast` passes `--quick`, a smoke test and never a result).

Definitions: `smc homo` = `homogeneous: true`; `ws homo` = `ws_xy_variation: false` (true a, m, sigma_w, sigma_s = 0.5, 3, 500, 100 everywhere); `ws hetero` = m and sigma_s vary along x and a, sigma_w change below horizon 1 (`sweeps.HETERO_LAYER_PARAMS`); `beta` = `param_grid.beta`, `gamma` = temporal smoothing (3 epochs); freed in the order sigma_s, m, sigma_w, a as in the surface-vs-full study. Probe layouts are written to `probes/*.csv` and passed with `--probe-xyz`; the pipeline re-anchors a probe file at the survey origin, so every layout contains x = 0 (`clustered` = the first n survey points, `random` = x = 0 plus n-1 seeded random points). Layouts that coincide (n = 1, n = 10) are run once. The calibration start of the free m, sigma_w, sigma_s is shifted by `--p0-bias` (default +20 %): with a homogeneous WS truth the repo default `lab_p0` is the truth itself.

Run log: the study writes to its own `mfc2_outputs/run_log_swc_study.csv` (override with `--log-file`), so its synthetic runs stay out of the shared real-data `mfc2_outputs/run_log.csv`; `compare_scenarios.sh` only sees the shared log unless you pass `--log-file mfc2_outputs/run_log_swc_study.csv`.

Outputs in `comparison_output/swc_design_study/`: `study_summary.csv` (RMSE / MAE / bias / R2 vs truth, error at and away from probe positions, per layer), `study_report.md`, and

## EM inversion method and speed

Why: the scenarios' `param_grid.method = ["ROPE"]` (EMagPy default `rep = 100` random samples per point, never set by the pipeline) does not fit the data. On the synthetic study truth (`diagnose_ec_inversion.py`, one realization): ECa misfit about 600 %, inverted EC 2-8 x too high, K = 0 floor (all four WS parameters known) theta RMSE 0.15 m3/m3; with L-BFGS-B misfit about 5 % and floor about 0.02. Fixed depths and the forward model (CS / FSlin) made no difference to that bias. The scenario files used to carry ROPE; they now carry L-BFGS-B, which is also the default of every script (`lbfgsb`; `lbfgsbfix` for the synthetic study). ROPE stays available as `--em-method rope` (or `python em_options.py --config <file> --em-method rope`). alpha / beta / gamma smoothing work with L-BFGS-B too. Depth modes: in the real scenarios ROPE already ran with fixed depths (all but `real_single_depth_free` and `real_multi_depth_free`); in the synthetic ones it ran with FREE depths, which is why the study needs `lbfgsbfix` to be fast.

Time (one core, 60 points, 4 layers, ms per point and ensemble member):

| | CS | FSlin |
|---|---|---|
| ROPE, fixed depths (real scenarios before the switch) | 26 | 153 |
| **L-BFGS-B, fixed depths** | **6.6** | **106** |
| ROPE, free depths | 39 | 165 |
| L-BFGS-B, free depths | 78 | 1149 |

So L-BFGS-B only saves time with fixed depths (CS x4, FSlin x1.4; with the 2-layer `real_single_*` setup x5 / x3). With free depths it is slower (CS x2, FSlin x7). The forward model is the other big lever: FSlin costs about 16 x CS, so a map whose selected members use FSlin is far more expensive than one that uses CS. Mapping time is (K selected members) x (epochs) x (EM points) x (cost per point): the calibrate stage already prunes the ensemble to K, `em_subsample` (grid thinning) shortens test maps, and `--em-njobs` uses idle cores. In a `--quick` synthetic pipeline run (FSlin only, 10 points per task) Step 1 took about 1.4 s per task with `lbfgsbfix` against about 11 s with free-depth L-BFGS-B. These are timings from a one-core sandbox, not from your real data: measure a map on your machine before relying on the ratios.

```bash
python diagnose_ec_inversion.py                   # ~8 min: tests fixed_depths / forwardModel / method one at a time
python diagnose_ec_inversion.py --tests T0 T3     # controls + method only (T6 = slow ROPE with more samples)
python ws_param_check.py                          # EC range, floor, a/sigma_w/sigma_s degeneracy, sensitivity (numpy only)
```

`ws_param_check.py`: in the generator's form `EC = theta^m / a * (sigma_w + sigma_s)` only `C = a / (sigma_w + sigma_s)` and `m` matter, so a, sigma_w and sigma_s cannot be told apart (judge recovery on C and m). Tests: `pytest tests/test_em_options.py tests/test_diagnose_ec_inversion.py`.

## Real-data runs: initial EC range, initial WS, and how big the ensemble is

### Initial ECmin/ECmax and initial WS for real runs (implemented)

The synthetic plot `synthetic_ws_truth_vs_initial.png` needs a truth, so it is not drawn for real data. For real runs Step 1d now also writes, in `<run>/initial_model/`:

* `initial_ec_range_by_horizon.png`: one column per horizon. Top row: histogram of the EC_bulk implied by the TDR theta of that horizon and the **initial** WS values, `EC_init = (sigma_w + sigma_s) * theta^m / a`, with ECmin/ECmax (`cond_ranges`) as vertical lines. Bottom row: XY map of the TDR probes coloured by EC_init (time mean) on the scale [ECmin, ECmax], a red "x" marks a probe outside the range. The title counts how many TDR-implied values fall outside the range.
* `initial_ws_by_horizon.png`: one panel per horizon, the four initial WS values as a position inside their calibration bounds, `[fixed]`/`[free]` from `ws_fixed_params`, red edge + "ON BOUND" when a value sits on a bound.

Initial WS values and ECmin/ECmax are constants per horizon, so an XY map of them would be a single colour; the XY map shows what varies in space (the TDR-implied EC). Horizon of a TDR depth = position among `depths0` (e.g. `depths0=[0.225]`: 15 cm -> H0, 30 cm -> H1). Tests: `tests/test_initial_ec_ws_real.py`. The plot code is pure numpy/matplotlib and never aborts the run.

Observation for `real_*_base` (`lab_p0 = [0.5, 3.0, 500, 100]`): `a = 0.5` sits exactly on the default lower bound of `a` (`WS_BOUNDS`). It is harmless while `a` is fixed (`real_single_base`), but in any real scenario that frees `a` it would pile up on the bound (see the free4 case in `to-do.md`); the new WS figure flags it.

### Is the ensemble generated at the TDR points or at all points? (answered)

At **all** EM points. Step 1 dispatches one inversion task per (alpha, forward model, starting-conductivity combination, epoch), and each task inverts the whole filtered survey file. For `real_single_base`: 5 alphas x 2 forward models x 4 starting combinations (2 layers, ECmin/ECmax) x 7 epochs = 280 tasks, and the 7 filtered surveys hold 83 827 / 29 048 / 64 409 / 55 770 / 21 191 / 45 513 / 41 319 points (341 077 per combination). The TDR probes (20) enter only afterwards: they are matched to the nearest EM points (`window_m`) to calibrate Waxman-Smits in Steps 2/4; the inverted EC at all other points is converted to theta with the calibrated parameters. That is why the run is slow, and why the 20 probes matter for calibration but not for the cost.

Whether the ensemble can be restricted to the TDR points without changing the result at those points: with `beta = 0` and `gamma = 0` (what the real scenarios use) I expect every EM point to be inverted independently, so the inversion at a probe's matched point should be identical in a full and in a reduced run. I did not run this; the acceptance test below checks it.

### Skimming the dataset for testing: `em_subsample` (implemented)

Scenario field `em_subsample` (module `em_subsample.py`), `null`/`{"mode": "off"}` = every filtered point. It thins each EM survey **after** `preprocess_em_survey` (the rolling mean needs the full sequence) and **before** the inversion and `match_epochs_to_reference_grid`; the processed CSV (regenerated from the raw file on every run) is rewritten in place, rows keep their order.

| mode | keys | what it keeps |
|---|---|---|
| `grid` | `cell_m` | one point per `cell_m` x `cell_m` cell, the one closest to the cell centre. The grid is absolute (origin 0 in the survey CRS), so the same cells are chosen in every epoch and the epochs still overlap (random thinning would not). Keep `cell_m` < `spatial_match_tolerance_m` (3 m). Best general choice. |
| `probes` | `radius_m` | points within `radius_m` of a TDR probe. Fastest; enough to test calibration (Steps 2/4/5), not the maps. The nearest EM point of 16 of the 20 probes was 1.1-3.2 m away in the last run, so use `radius_m >= 5`. |
| `stride` | `stride` | every n-th point (smoke test). |
| `random` | `max_points`, `seed` | random subset (smoke test). |

Common key `keep_probe_nearest` (default `true`): the EM point nearest to each TDR probe is always kept. The setting is part of the Step 1 cache fingerprint (added only when thinning is on, so existing caches keep their hash), is printed in the scenario banner and the report config table, and the per-file point counts appear in the preprocessing table ("Final pts" = after thinning). Ready-made scenarios: `real_single_test_grid` (`grid`, 3 m) and `real_single_test_probes` (`probes`, 5 m), both copies of `real_single_base` with their own `output_dir`/`cache_tag`.

```bash
./run_one_scenario.sh -s real_single_test_grid   -c ensemble_scenarios_real.json
./run_one_scenario.sh -s real_single_test_probes -c ensemble_scenarios_real.json
```

Caveat: with a lateral-smoothing `beta > 0` (CLI `--beta`) thinning changes the neighbourhoods the smoothing acts on; for `beta = 0` points are independent.

### Smoke-testing the ensemble: `--quick` (implemented)

`em_subsample` thins the data and leaves the ensemble alone; `--quick` is the opposite: it keeps all the data and shrinks the ensemble (module `quick_preset.py`).

| flag | effect | `real_single_base` |
|---|---|---|
| (none) | full grid | 5 alphas x 2 forward models x 4 starts x 7 epochs = 280 tasks |
| `--quick` | one alpha (the **middle** of the alpha list, i.e. the geometric centre of the log sweep) and one forward model (the **first**, FSlin) | 1 x 1 x 4 x 7 = **28** |
| `--quick --quick-epochs 3` | also N evenly spaced epochs, first and last always kept | 1 x 1 x 4 x 3 = **12** |

```bash
./run_one_scenario.sh -s real_single_base -c ensemble_scenarios_real.json --quick
./run_one_scenario.sh -s real_single_base -c ensemble_scenarios_real.json --quick --quick-epochs 3
./run_real_all_scenarios.sh --quick --quick-epochs 3        # the whole real-case script, reduced
./run_real_all_scenarios.sh --quick 425 5325                # combines with the drop-coils override
```

It never touches the EM/TDR data (no point dropped; TDR probes unchanged), and `--beta` / `--gamma` still apply on top. Starting-conductivity combinations and `method` are left as the scenario defines them. Safeguards:

- **Smoke test, not a result.** The ensemble (alpha x forward model x starting conductivities) is the scientific object of the method; with one alpha and one forward model the ensemble ranking, stacking depth K and spread are not meaningful. It is meant for checking that a scenario runs end to end and for looking at the plots.
- **Full-run cache is never overwritten.** A quick run reads/writes its own `ensemble_cache_<tag>_quick[_eN].pkl`; the grid and the epoch list are also in the cache fingerprint (epochs only when a subset is used, so existing caches keep their hash).
- **Visible in the output.** Run folder `<seq>_<scenario>_quick`, a `[QUICK]` banner (what was kept, task count) and a "quick preset" row in the report's runtime-arguments table.
- `--quick-epochs` needs `--quick`, is real-data only, and always keeps epoch 0 (Step 1d plots the first survey).
- Under `--quick`, scenarios that differ from the base only by forward model (`*_fslin`, `*_cs`) all collapse to one model, so they stop being a comparison; `compare_scenarios` across them is only a plumbing check.

### Why does the pipeline currently use all points? (my reading of the code, not a documented decision)

There is no step that needs all points for the calibration itself, so I would call it a consequence of how the code grew, not a requirement. Plausible reasons:

* The pipeline was built on synthetic 1-D/2-D grids where every point is cheap, and its products are full maps (`water_content_xz/xy`, `cv_map`, `is_calibrated`, per-horizon EC/theta maps): those need every point.
* Step 1 produces one `models_clean` array on the union reference grid, and Steps 2-5 read the probe-matched points out of it, so calibration and mapping share one run and one cache.
* The probe match averages EM points inside `window_m` (1 m) around each probe (nearest-point fallback otherwise), so a few neighbours of every probe are needed; that argues for `radius_m >= window_m`, not for all 341 077 points.
* Diagnostics (matching plots, footprint, transects) are drawn on the whole survey.

The cost, not the science, is what pushes toward a split (next section).

### Split for the final runs: `--stage calibrate` / `--stage map` (implemented)

Calibration only needs the probe-matched points; the maps need all points.

```bash
# 1. calibrate: EM points restricted to the probe neighbourhoods, FULL ensemble
#    (all alphas / forward models), Steps 0-5; writes stage_calibration.json; stops before Step 6
./run_one_scenario.sh -s real_single_base -c ensemble_scenarios_real.json --mode 2d --stage calibrate

# 2. map: all (or grid-thinned) points, ONLY the selected alpha / forward model / K
./run_one_scenario.sh -s real_single_base -c ensemble_scenarios_real.json --mode 2d --stage map \
    --calibration <output>/<scenario>_calibrate        # folder or stage_calibration.json
```

Use a scenario with no `em_subsample` (e.g. `real_single_base`) for both stages: `--stage calibrate` restricts the EM points to the probe neighbourhoods itself (radius 5 m unless the scenario sets `em_subsample.mode = "probes"` with its own radius), and `--stage map` then uses all points. A scenario that already thins with `mode = "probes"` (e.g. `real_single_test_probes`) would map only the probe neighbourhoods.

Each stage has its own run folder suffix and cache file. Use the same scenarios file (same `param_grid.method`, `fixed_depths`) for both stages: the map looks the calibrated members up by method and stops if they are missing. The map stage has only K members x epochs Step-1 tasks, so with `--em-njobs auto` (default) the points of each task are split across the idle cores when the method is deterministic (see "EM inversion method and speed"). `--stage map` checks that depths0 / cond_ranges / epochs match the calibration before inverting anything, re-fits Steps 2-5 on the selected members and reports the drift against the calibration (`[WARN] CALIBRATION DRIFT` means: redo calibrate). `--stage map` cannot be combined with `--quick`.

**How `ws_localized_bandwidth_sweep` fits in.** The leave-one-probe-out CV only reads probe-matched points, so it runs in `--stage calibrate` only (on the full ensemble, against its rank-1 member). The chosen bandwidth is stored in `stage_calibration.json` (`localized_bandwidth`, `bandwidth_from_sweep`). In `--stage map` the sweep is skipped (logged as `[STAGE] map: ws_localized_bandwidth_sweep skipped`) and the stored bandwidth is reused as a fixed `ws_localized_bandwidth` for the kernel-localized fit, which is then evaluated at every map point (the kernel only needs probe data + target coordinates, so thinning the EM points does not change the fit, only where it is evaluated). Passing `--ws-localized-bandwidth C` to the map run overrides the stored value; the sweep list on the map CLI/scenario is ignored. The localized fit now feeds the maps (next section); it still does not feed Steps 2-5 (ensemble ranking, K, the reported RMSE).

### Maps with localized Waxman-Smits: `--ws-map-calibration {localized,global}` (default `localized`)

After Step 5 has chosen K, the optimal averaged EC model is converted to water content with the **kernel-localized** Waxman-Smits fit instead of one global set per horizon: every EM point gets the `(a, m, sigma_w, sigma_s)` fitted for it (probe observations weighted by a Gaspari-Cohn kernel of their distance, radius `c`). Nothing is re-inverted: the fit only reads the probe-matched EC and the TDR theta, and is evaluated at every point (`localized_mapping.py`).

* **Fallback.** The kernel is exactly zero beyond `2c`. A point of a horizon with no probe inside that radius uses the **global per-horizon fit of Step 4 at K** (not the lab prior); so does a horizon with no probe, or a non-finite localized parameter. The log gives the share of points on the fallback per horizon and warns above 50 %.
* **Bandwidth.** Same resolution as the diagnostic: LOO-CV sweep result > `--ws-localized-bandwidth` > value stored by `--stage calibrate` (map stage) > scenario `ws_localized_bandwidth`. All real scenarios carry a sweep, so real runs are localized by default. With no bandwidth at all (every synthetic scenario) the maps stay global and the log says why.
* **What does not change.** Ensemble ranking, K, the Step 5 RMSE, the drift report of `--stage map` and the Step 4 plots are the global ones. `theta_calc.npy` (and so every water-content map) is the localized one; `output_model/` also gets `theta_calc_global.npy`, `ws_localized_params.npy` (4, n_layers, n_points: a, m, sigma_w, sigma_s after the fallback), `ws_localized_fallback.npy` and `ws_localized_bandwidth.npy`.
* **Validation.** With a train/val split, Step 5b also logs `Validation RMSE (localized)`: the localized parameters (fitted on the train probes only) evaluated at the held-out probes, next to the global `Validation RMSE`.
* **Opt out.** `--ws-map-calibration global` gives one parameter set per horizon, the previous behaviour; it is the sensible choice when the field is homogeneous. Through the hypothesis scripts: `python run_all_hypotheses.py ... -- --ws-map-calibration global`.
* **Limits.** The same bandwidth is used for every horizon. Few probes inside `2c` make a 4-parameter local fit weakly constrained (it is regularised towards the lab prior `lab_p0`, not towards the global fit): check `ws_localized_fallback.npy` and the sweep table before trusting a small `c`. Horizon routing in the localized fit is the plain probe-to-layer one (no `probe_depths_reflect_fitted_interfaces` handling).

### Optional: calibrate Waxman-Smits by zone (future, clustering method to be discussed)

For real data it would be convenient to optionally cluster the field into zones and run one WS calibration per zone (instead of one set of parameters per horizon for the whole field). How to cluster is open. Candidates to discuss:

* **Geographic / management zones** (plots, crops, user-drawn polygons): simplest, easy to explain, needs a polygon file.
* **ECa-based clustering** (k-means / Gaussian mixture on time-mean ECa per coil, as in precision agriculture): data-driven, but circular, because the zones are defined by the same quantity that is then converted to theta.
* **Soil-map / texture-based** (external soil map, clay content): physically closest to what a, m and sigma_s represent.
* **Temporal-stability based** (zones with persistent ECa pattern across the 7 epochs).

**Possibly redundant with `ws_localized_bandwidth_sweep`.** The localized Step 2 fit (`run_petro_localized`) already lets the WS parameters vary in space: it fits a separate parameter set at every target location, weighting every TDR observation of the horizon by a Gaspari-Cohn kernel of its distance (`bandwidth -> inf` = the global per-horizon fit, `bandwidth -> 0` = nearest probe), and the bandwidth is chosen by leave-one-probe-out CV. Zones are the hard-partition version of the same idea. Where they differ:

* Localized fit: no clustering decision, one hyperparameter chosen by CV, smooth variation. But it only knows distance: it smooths across an abrupt soil boundary and cannot pool probes from two separate areas that share the same soil.
* Zones: can use a covariate (ECa, soil map, texture) so non-adjacent areas share parameters and sharp boundaries are respected, with more probes pooled per fit and parameters that are easy to interpret. But they add the clustering choice and need enough probes per zone.
* Both can be combined (kernel weights multiplied by a same-zone indicator, or a distance that includes the covariate), at the price of more complexity.

Suggested decision rule before building anything: look at what the bandwidth CV selects on the real data. If it picks a bandwidth much larger than the field, there is no spatial structure to exploit from 20 probes and zones are not worth it; if it picks a small one, there is structure, and zones are worth it only if a covariate or a boundary explains it that distance alone cannot. I have not seen that CV output for the real runs.

Things to settle with it: minimum number of TDR probes per zone (20 probes in total, so only a few zones; free parameters per zone must stay below what the probes can constrain); what a zone without a probe falls back to (global parameters or nearest zone); leave-one-probe-out CV must respect the zones; relation to the existing continuous alternatives (`ws_xy_variation`, localized Gaspari-Cohn fit `ws_localized_bandwidth_sweep`). Sketch: scenario field `ws_zones` (`null` | `{"method": "polygons"|"kmeans_eca"|"file", ...}`) producing a zone label per reference-grid point, and Steps 2/4 calibrating per (horizon, zone).

### Acceptance tests for the above

* A `grid` or `probes` run reproduces, at the probe-matched points, the optimal EC and theta of the full run (same `ec_optimal`, `theta_calc` within solver tolerance).
* Probe-to-EM matching report is unchanged (same matched indices/distances) or only gets closer.
* Cache fingerprint changes when `em_subsample` changes.

## Reading the RMSE and comparing many runs

* Every run reports the RMSE in **% vol** (m³/m³ × 100) and normalised by the spread of the measured SWC: `RSR = RMSE / std(observed SWC)` (≤ 0.5 very good, 0.5–0.6 good, 0.6–0.7 satisfactory, > 0.7 unsatisfactory, ≥ 1 no skill). See `rmse_context.py`.
* `run_log.csv` has the columns `study_type`, `rmse_pct`, `swc_obs_std`, `rsr`, `rmse_rating`. Add them to an existing log with `python run_log.py upgrade --log mfc2_outputs/run_log.csv`.
* `python plot_run_log.py [--study-type ...] [--compare]` writes all summary plots per study type to `comparison_output/run_log_plots/`; `python plot_swc_study_log.py` does the same for `run_log_swc_study.csv`.
* `python study_status.py` writes `STUDY_STATUS.md`: per study type what is done, failed or missing (with the commands to run it) and the caveats found in the run manifests.
* Runs write `output_model/maps.nc` (theta, uncertainty, coordinates; `maps_export.py`, needs `xarray` + `netcdf4`). `python plot_run_log.py --maps` redraws the maps of all runs of a study on one shared colour scale; `--figures --tile` gathers the existing PNGs.
