# mfc2_EA-EM_TDR

EA-EM pipeline: ensemble EM (ECa) inversion + TDR-calibrated Waxman-Smits petrophysics → soil water content. Works on synthetic scenarios and on real MFC2 field data.

Outputs go to `mfc2_outputs/<scenario output_dir>/<NNNN>_<scenario>/`; every run is appended to `mfc2_outputs/run_log.csv`.

## Installation

Requires Python >= 3.12 (results were produced with 3.12). The repository is a set of scripts, not an installable package: clone it, install the dependencies, and run everything from the repository root.

```bash
git clone https://github.com/BenjMy/mfc2_EA-EM_TDR
cd mfc2_EA-EM_TDR
```

With conda:

```bash
conda env create -f environment.yml
conda activate eaem
```

Or with pip / venv:

```bash
python3.12 -m venv ~/venvs/eaem
source ~/venvs/eaem/bin/activate
pip install -e ".[dev]"
```

Dependencies: `numpy`, `scipy`, `pandas`, `matplotlib`, `tqdm`, `emagpy` (`pytest` for the tests). Check the install with `pytest tests` and `./run_one_scenario.sh --list`. The launchers are bash scripts; on Windows use WSL or Git Bash. Numerical results can differ slightly between Python/library versions, so compare runs only within one environment.

## Run one scenario

```bash
./run_one_scenario.sh --list                          # list scenarios
./run_one_scenario.sh --validate                      # validate ensemble_scenarios.json
./run_one_scenario.sh -s 1d_surface_tdr --mode 1d --num-swc-positions 5   # synthetic, 1-D transect
./run_one_scenario.sh -s 2d --mode 2d                 # synthetic, 2-D grid
./run_one_scenario.sh --mode 2d -s real_single_base -c ensemble_scenarios_real.json   # real data (paths set in the JSON)
python run_all_hypotheses.py --fast --dry-run             # real data: the three hypothesis tests, plan only
./run_one_scenario.sh --help                          # all options
```

Scenarios are defined in `ensemble_scenarios.json` (synthetic) and `ensemble_scenarios_real.json` (real). A scenario can start from another one with `"extends": "<name>"` (nested objects are merged, lists/scalars replaced); `ws_layer_params` sets per-layer true Waxman-Smits parameters for synthetic data. The surface-vs-full study families `1d_{surface,full}_free{K}` and `1d_{surface,full}_hetero_free{K}` are generated by `sweeps.py` from the two base scenarios `1d_surface_tdr` / `1d_full_depth_ref` (they are not in the JSON; an entry of the same name in the JSON would override the generated one). `python scenario_loader.py --list-scenarios` lists everything, generated names included.

Tests: `pytest tests`.

## Input data paths (`EA_EM_config.py`)

All input paths of the real-data branch live in `EA_EM_config.py`, grouped as a named *dataset* (`em_dir`, `tdr_dir`, `coord_file`). `mfc2` is the built-in default, so existing runs are unchanged. To use another site, add a dataset (edit `DATASETS`, or put it in `EA_EM_datasets.json` next to the file) and select it:

```bash
python EA_EM_config.py --list                 # known datasets
python EA_EM_config.py --dataset my_site --check   # do the paths exist?
./run_one_scenario.sh --mode 2d -s real_single_base -c ensemble_scenarios_real.json --dataset my_site
EA_EM_DATASET=my_site ./run_one_scenario.sh ...    # same, through the environment
```

Precedence: explicit `--em-dir/--tdr-dir/--coord-file` > `--dataset` > paths written in the scenario JSON > `$EA_EM_DATASET` > `mfc2`. A real-data scenario may omit `em_data_dir`/`tdr_data_dir`/`coord_file` and take them from the dataset. `EA_EM_DATA_ROOT` relocates the default `./data` tree.

## Calibration options (real data)

What is calibrated, and over which units, is set **per scenario** in `ensemble_scenarios_real.json` (fields are inherited with `"extends"`); the input data come from `EA_EM_config.py` (see above). The Waxman-Smits (WS) parameters are `a`, `m`, `sigma_w`, `sigma_s`; horizons come from `depths0` and the probe depths (the real TDR sensors sit at 0.15 and 0.30 m).

| Calibration unit | Status | Where to set it |
|---|---|---|
| **One parameter set per horizon, pooled over all stations** | Default. Used by Steps 2, 4, 5 and by the maps. | `ws_fixed_params` (`true` = fixed, `false` = free; freed in the order `sigma_s`, `m`, `sigma_w`, `a` by the `hyp1` scenarios), `lab_p0` (start / fixed values), `ws_bounds` (default `a` 0.5-5, `m` 1-4, `sigma_w` 1-1000, `sigma_s` 0-200), `depths0` + `cond_ranges` (layers) |
| **Per EM point, kernel-weighted by the distance to the stations** (Gaspari-Cohn) | Diagnostic only: `petro_calibration_localized*.png`, bandwidth chosen by leave-one-probe-out CV. It does **not** reach Step 5 / the maps. | `ws_localized_bandwidth` or `ws_localized_bandwidth_sweep` in the scenario, or `--ws-localized-bandwidth[-sweep]`. The bandwidth is in metres: use values of the order of the station spacing (the MFC2 stations are 20-32 m apart, so a sweep below about 20 m cannot show anything) |
| **Per station** | Not available in Step 5 / maps (see `to-do.md`). | - |
| **Per zone (cluster of stations)** | Not available (see `to-do.md`). | - |

**Train / validation split** (`train_val_split`, or `hyp2_train_val_split.py`): this is a way to *validate* the calibration, not another calibration unit. The training part drives the WS fit **and** the choice of K; the validation part is held out and used once at the end to report an unbiased RMSE (Loiseau et al., 2026, Sec. 2.3 and 2.6). It can be done **by sensor**: `by_probe` holds out whole stations (fully independent, needs real probe ids, so real data only). The other methods are `off`, `alternate_sorted` (every other observation by sorted theta: not independent, the same probe or time step can be in both parts), `by_time_block` and `random`. With `off` the reported RMSE is in-sample and optimistic (0.092 vs a leave-one-probe-out 0.112 in the first real run).

## Running several real-data scenarios

The launchers form three levels. Each level only calls the one below it, and only `run_one_scenario.sh` does the computing:

```
run_all_hypotheses.py            ONE entry point: runs the hypothesis scripts below in turn
 |-- hyp1_layers_ws_freedom.py      H1  how many layers / how many free WS parameters
 |-- hyp2_train_val_split.py        H2  is the calibration good on held-out data
 `-- hyp3_localized_bandwidth.py    H3  does a localized WS calibration help, which bandwidth
       (each generates its scenarios with hyp_common.py, then calls the level below)
run_one_scenario.sh              ONE run of ONE scenario  ->  run_pipeline.py
run_real_all_scenarios.sh        fixed batch of run_one_scenario.sh calls (paper comparisons)
```

| Script | Question / role | Scenarios it uses |
|---|---|---|
| `run_one_scenario.sh` | One run of one scenario: `-s <name> -c <json>`. | Any scenario of the JSON you pass. |
| `hyp1_layers_ws_freedom.py` | **H1**: how many layers can the real TDR sensors support (they sit at 0.15 and 0.30 m), and how many Waxman-Smits parameters (sigma_s, m, sigma_w, a) can be freed? Layer designs `L2`/`L3`/`L4` (or `--design NAME=d1,d2`) x K free parameters. Prints which horizons have no sensor before running. | Generated `real_study_<design>_free<K>`. |
| `hyp2_train_val_split.py` | **H2**: the default run fits and selects K on all TDR data, so its RMSE is in-sample. Runs the same scenario with each split (`off`, `alternate_sorted`, `by_probe`, `by_time_block`, `random`) and reports the held-out RMSE. | Generated `real_tv_<method>` (from `--base`). |
| `hyp3_localized_bandwidth.py` | **H3**: does letting WS parameters vary in space (kernel-localized fit) beat one set per horizon, and at which bandwidth? Runs one scenario with your candidate list (`--bandwidths`), chosen by leave-one-probe-out CV. | Generated `real_bw_sweep` (from `--base`). |
| `hyp_common.py` | Not run directly: the shared engine of the three `hyp*` scripts (generate scenarios, write `<hyp>_scenarios.json`, print the plan, run `run_one_scenario.sh` per scenario, collect `<hyp>_summary.csv`). Defines the options they all share: `--config --base --mode --stage --out-dir --fast --dry-run --keep-going`, and forwards anything after a bare `--` to `run_one_scenario.sh`. | None (it generates nothing itself). |
| `run_all_hypotheses.py` | All of the above with their shared options (`--config --base --mode --stage --fast --dry-run --keep-going`); `--only 1 3` picks some, `--list` shows them. | Whatever the three scripts generate. |
| `run_real_all_scenarios.sh` | The fixed paper batch: `real_single_*` / `real_multi_*` (forward model `_base` / `_fslin` / `_cs`, fixed vs free interfaces `_depth_free`, WS freedom `_ws_*`), then `--beta`, `--gamma` and bandwidth sweeps and (commented out) `--train-val-split`. It starts with `--list` and `--validate`. Does not generate anything. | The existing `real_single_*` (2 layers) and `real_multi_*` (4 layers). |

The hypothesis scripts run `--stage calibrate` by default (probe neighbourhoods only, Steps 0-5), because all three are about the calibration quality; `--stage none` does the full run; `--stage both` runs, for every scenario, `--stage calibrate` and then `--stage map --calibration <that calibrate run folder>` (Step 6 on all EM points, inverting only the K selected members). If a calibrate run fails its map is skipped; with `--fast` the map is skipped too, because `--stage map` cannot be combined with `--quick`. The summary CSV has a `stage` column (one row per scenario and stage). `both` maps every scenario, which is expensive for exploratory variants you will discard (e.g. `L3`/`L4` horizons without a sensor): use `calibrate` to compare, then `both` on the chosen scenario. Each writes `<out-dir>/<hyp>_scenarios.json` (the generated scenarios; your JSON is not edited) and `<out-dir>/<hyp>_summary.csv` (final RMSE, CV score, ensemble size, runtime per scenario), under `mfc2_outputs/hypotheses/<hypothesis>/`. Step 1, the expensive ensemble inversion, is shared between the variants of one hypothesis. To add a hypothesis, copy `hyp3_localized_bandwidth.py`, change its question and scenario generator and register it in `run_all_hypotheses.py`. None of this has been run on the real data yet (see `run_paper_real.md`, a cheapest-first check that the dataset works with the pipeline).

```bash
python run_all_hypotheses.py --list                      # the hypotheses, nothing run
python run_all_hypotheses.py --fast --dry-run            # plan of all three
python run_all_hypotheses.py --fast                      # smoke test of all three (not a result)
python run_all_hypotheses.py --only 2 3 --base real_L3_base    # H2 and H3 on the 3-layer scenario
python hyp1_layers_ws_freedom.py --designs L3 --free-k 1 2     # one hypothesis, its own options
python run_all_hypotheses.py --stage both --dry-run      # plan: calibrate, then map, for every scenario
python run_all_hypotheses.py --only 3 --stage both       # H3: calibrate then map
python run_all_hypotheses.py --stage none                # full run instead of calibrate (no map hand-over)
python run_all_hypotheses.py --keep-going --out-root my_out   # continue after a failure; other output root
python hyp1_layers_ws_freedom.py --stage both --dry-run  # any hyp script takes the same shared options
python hyp2_train_val_split.py --base real_L3_base --mode 1d --out-dir my_out/hyp2   # --config/--base/--mode/--out-dir
python hyp3_localized_bandwidth.py --bandwidths 1 2 5 10 15 20 --footprint
./run_real_all_scenarios.sh --quick --quick-epochs 3     # the fixed paper batch, reduced (smoke test)
./run_real_all_scenarios.sh 425 5325                     # same, overriding the dropped coils / frequencies
```

Flags after a bare `--` go to `run_one_scenario.sh` (for example `-- --em-footprint-diagnostic`). Compare the resulting runs with `./compare_scenarios.sh` (next section). `real_single_ws_free_all` (all four WS parameters free, `a` started off its lower bound with `ws_bounds`) is part of the WS-freedom loop of `run_real_all_scenarios.sh`.

### Changing the number of layers (real data)

The number of layers is not a command-line option: it comes from the scenario. `depths0` lists the interface depths (m) and `cond_ranges` needs one `[min, max]` per layer, so **N layers = N-1 interfaces and N `cond_ranges` entries**.

| Scenario | `depths0` | Layers | Notes |
|---|---|---|---|
| `real_single_*` | `[0.225]` | 2 | |
| `real_L3_base` | `[0.225, 0.6]` | 3 | Extends `real_single_base`; use it for both `--stage calibrate` and `--stage map`. |
| `real_single_test_probes_L3` | `[0.225, 0.6]` | 3 | Extends `real_single_test_probes` (probe points only): smoke test of the calibration, not for maps. |
| `real_multi_*` | `[0.3, 0.6, 1.0]` | 4 | |

The real TDR sensors are only at 0.15 m and 0.30 m. A horizon without a sensor cannot be calibrated and keeps the prior WS parameters (`lab_p0`); in `real_L3_base` that is H2 (below 0.6 m), and in `real_multi_*` (15 cm in H0, 30 cm in H1) it is H2 (0.6-1.0 m) and H3 (below 1.0 m). `hyp1_layers_ws_freedom.py` prints this coverage before it runs anything.

```bash
./run_one_scenario.sh -s real_L3_base -c ensemble_scenarios_real.json --mode 2d --stage calibrate
python hyp1_layers_ws_freedom.py --designs L3 --free-k 2 --dry-run   # same layers x 2 free WS parameters, plan only
python run_all_hypotheses.py --only 2 3 --base real_L3_base        # H2 and H3 with 3 layers
```

## Number / distribution of SWC probes study (1-D synthetic)

`study_swc_design.py` generates the scenarios, runs them, scores `theta_calc` against the synthetic truth and draws the comparison figures. Factors: number of SWC positions `n` (1, 2, 3, 5, 10), their distribution (`spread` / `clustered` / `random`), truth soil moisture (`smc` homo / hetero), truth Waxman-Smits parameters (`ws` homo / hetero), number of free WS parameters `K` (1-4) and the EMagPy regularisation (`noreg` / `beta` / `gamma` / `both`).

```bash
python study_swc_design.py --dry-run                      # write + validate the scenarios, print the commands
python study_swc_design.py --preset smoke --fast          # smoke test of the whole chain (8 short runs)
python study_swc_design.py --preset oat                   # one factor at a time around the reference (15 runs)
python study_swc_design.py --preset main --keep-going --resume   # truth x K x n, + distribution and reg at n = 5 (160 runs)
python study_swc_design.py --analyze-only                 # redo summary + figures from the run log
python study_swc_design.py --smc homo hetero --ws hetero --free-k 2 4 --n-swc 1 3 5 10   # any subset of the levels
```

Presets: `smoke` 8, `oat` 15, `main` 160, `full` 704 runs. A synthetic run always repeats Step 1 (the ensemble cache is real-data only), so each run costs a full pipeline run (3-5 min; `--fast` passes `--quick`, a smoke test and never a result).

Definitions: `smc homo` = `homogeneous: true`; `ws homo` = `ws_xy_variation: false` (true a, m, sigma_w, sigma_s = 0.5, 3, 500, 100 everywhere); `ws hetero` = m and sigma_s vary along x and a, sigma_w change below horizon 1 (`sweeps.HETERO_LAYER_PARAMS`); `beta` = `param_grid.beta`, `gamma` = temporal smoothing (3 epochs); freed in the order sigma_s, m, sigma_w, a as in the surface-vs-full study. Probe layouts are written to `probes/*.csv` and passed with `--probe-xyz`; the pipeline re-anchors a probe file at the survey origin, so every layout contains x = 0 (`clustered` = the first n survey points, `random` = x = 0 plus n-1 seeded random points). Layouts that coincide (n = 1, n = 10) are run once. The calibration start of the free m, sigma_w, sigma_s is shifted by `--p0-bias` (default +20 %): with a homogeneous WS truth the repo default `lab_p0` is the truth itself.

Run log: the study writes to its own `mfc2_outputs/run_log_swc_study.csv` (override with `--log-file`), so its synthetic runs stay out of the shared real-data `mfc2_outputs/run_log.csv`; `compare_scenarios.sh` only sees the shared log unless you pass `--log-file mfc2_outputs/run_log_swc_study.csv`.

Outputs in `comparison_output/swc_design_study/`: `study_summary.csv` (RMSE / MAE / bias / R2 vs truth, error at and away from probe positions, per layer), `study_report.md`, and

## Real-data runs: initial EC range, initial WS, and how big the ensemble is

### Initial ECmin/ECmax and initial WS for real runs (implemented)

The synthetic plot `synthetic_ws_truth_vs_initial.png` needs a truth, so it is not drawn for real data. For real runs Step 1d now also writes, in `<run>/initial_model/`:

* `initial_ec_range_by_horizon.png`: one column per horizon. Top row: histogram of the EC_bulk implied by the TDR theta of that horizon and the **initial** WS values, `EC_init = (sigma_w + sigma_s) * theta^m / a`, with ECmin/ECmax (`cond_ranges`) as vertical lines. Bottom row: XY map of the TDR probes coloured by EC_init (time mean) on the scale [ECmin, ECmax], a red "x" marks a probe outside the range. The title counts how many TDR-implied values fall outside the range.
* `initial_ws_by_horizon.png`: one panel per horizon, the four initial WS values as a position inside their calibration bounds, `[fixed]`/`[free]` from `ws_fixed_params`, red edge + "ON BOUND" when a value sits on a bound.

Initial WS values and ECmin/ECmax are constants per horizon, so an XY map of them would be a single colour; the XY map shows what varies in space (the TDR-implied EC). Horizon of a TDR depth = position among `depths0` (e.g. `depths0=[0.225]`: 15 cm -> H0, 30 cm -> H1). Tests: `tests/test_initial_ec_ws_real.py`. The plot code is pure numpy/matplotlib and never aborts the run.

Observation for `real_*_base` (`lab_p0 = [0.5, 3.0, 500, 100]`): `a = 0.5` sits exactly on the default lower bound of `a` (`WS_BOUNDS`). It is harmless while `a` is fixed (`real_single_base`), but in any real scenario that frees `a` it would pile up on the bound (see the free4 case in `to-do.md`); the new WS figure flags it.

### Is the ensemble generated at the TDR points or at all points? (answered)

At **all** EM points. Step 1 dispatches one inversion task per (alpha, forward model, starting-conductivity combination, epoch), and each task inverts the whole filtered survey file. For `real_single_base`: 5 alphas x 2 forward models x 4 starting combinations (2 layers, ECmin/ECmax) x 7 epochs = 280 tasks, and the 7 filtered surveys hold 83 827 / 29 048 / 64 409 / 55 770 / 21 191 / 45 513 / 41 319 points (341 077 per combination). The TDR probes (20) enter only afterwards: they are matched to the nearest EM points (`window_m`) to calibrate Waxman-Smits in Steps 2/4; the inverted EC at all other points is converted to theta with the calibrated parameters. That is why the run is slow, and why the 20 probes matter for calibration but not for the cost.

Whether the ensemble can be restricted to the TDR points without changing the result at those points: with `beta = 0` and `gamma = 0` (what the real scenarios use) I expect every EM point to be inverted independently, so the inversion at a probe's matched point should be identical in a full and in a reduced run. I did not run this; the acceptance test below checks it.

### Skimming the dataset for testing: `em_subsample` (implemented)

Scenario field `em_subsample` (module `em_subsample.py`), `null`/`{"mode": "off"}` = every filtered point. It thins each EM survey **after** `preprocess_em_survey` (the rolling mean needs the full sequence) and **before** the inversion and `match_epochs_to_reference_grid`; the processed CSV (regenerated from the raw file on every run) is rewritten in place, rows keep their order.

| mode | keys | what it keeps |
|---|---|---|
| `grid` | `cell_m` | one point per `cell_m` x `cell_m` cell, the one closest to the cell centre. The grid is absolute (origin 0 in the survey CRS), so the same cells are chosen in every epoch and the epochs still overlap (random thinning would not). Keep `cell_m` < `spatial_match_tolerance_m` (3 m). Best general choice. |
| `probes` | `radius_m` | points within `radius_m` of a TDR probe. Fastest; enough to test calibration (Steps 2/4/5), not the maps. The nearest EM point of 16 of the 20 probes was 1.1-3.2 m away in the last run, so use `radius_m >= 5`. |
| `stride` | `stride` | every n-th point (smoke test). |
| `random` | `max_points`, `seed` | random subset (smoke test). |

Common key `keep_probe_nearest` (default `true`): the EM point nearest to each TDR probe is always kept. The setting is part of the Step 1 cache fingerprint (added only when thinning is on, so existing caches keep their hash), is printed in the scenario banner and the report config table, and the per-file point counts appear in the preprocessing table ("Final pts" = after thinning). Ready-made scenarios: `real_single_test_grid` (`grid`, 3 m) and `real_single_test_probes` (`probes`, 5 m), both copies of `real_single_base` with their own `output_dir`/`cache_tag`.

```bash
./run_one_scenario.sh -s real_single_test_grid   -c ensemble_scenarios_real.json
./run_one_scenario.sh -s real_single_test_probes -c ensemble_scenarios_real.json
```

Caveat: with a lateral-smoothing `beta > 0` (CLI `--beta`) thinning changes the neighbourhoods the smoothing acts on; for `beta = 0` points are independent.

### Smoke-testing the ensemble: `--quick` (implemented)

`em_subsample` thins the data and leaves the ensemble alone; `--quick` is the opposite: it keeps all the data and shrinks the ensemble (module `quick_preset.py`).

| flag | effect | `real_single_base` |
|---|---|---|
| (none) | full grid | 5 alphas x 2 forward models x 4 starts x 7 epochs = 280 tasks |
| `--quick` | one alpha (the **middle** of the alpha list, i.e. the geometric centre of the log sweep) and one forward model (the **first**, FSlin) | 1 x 1 x 4 x 7 = **28** |
| `--quick --quick-epochs 3` | also N evenly spaced epochs, first and last always kept | 1 x 1 x 4 x 3 = **12** |

```bash
./run_one_scenario.sh -s real_single_base -c ensemble_scenarios_real.json --quick
./run_one_scenario.sh -s real_single_base -c ensemble_scenarios_real.json --quick --quick-epochs 3
./run_real_all_scenarios.sh --quick --quick-epochs 3        # the whole real-case script, reduced
./run_real_all_scenarios.sh --quick 425 5325                # combines with the drop-coils override
```

It never touches the EM/TDR data (no point dropped; TDR probes unchanged), and `--beta` / `--gamma` still apply on top. Starting-conductivity combinations and `method` are left as the scenario defines them. Safeguards:

- **Smoke test, not a result.** The ensemble (alpha x forward model x starting conductivities) is the scientific object of the method; with one alpha and one forward model the ensemble ranking, stacking depth K and spread are not meaningful. It is meant for checking that a scenario runs end to end and for looking at the plots.
- **Full-run cache is never overwritten.** A quick run reads/writes its own `ensemble_cache_<tag>_quick[_eN].pkl`; the grid and the epoch list are also in the cache fingerprint (epochs only when a subset is used, so existing caches keep their hash).
- **Visible in the output.** Run folder `<seq>_<scenario>_quick`, a `[QUICK]` banner (what was kept, task count) and a "quick preset" row in the report's runtime-arguments table.
- `--quick-epochs` needs `--quick`, is real-data only, and always keeps epoch 0 (Step 1d plots the first survey).
- Under `--quick`, scenarios that differ from the base only by forward model (`*_fslin`, `*_cs`) all collapse to one model, so they stop being a comparison; `compare_scenarios` across them is only a plumbing check.

### Why does the pipeline currently use all points? (my reading of the code, not a documented decision)

There is no step that needs all points for the calibration itself, so I would call it a consequence of how the code grew, not a requirement. Plausible reasons:

* The pipeline was built on synthetic 1-D/2-D grids where every point is cheap, and its products are full maps (`water_content_xz/xy`, `cv_map`, `is_calibrated`, per-horizon EC/theta maps): those need every point.
* Step 1 produces one `models_clean` array on the union reference grid, and Steps 2-5 read the probe-matched points out of it, so calibration and mapping share one run and one cache.
* The probe match averages EM points inside `window_m` (1 m) around each probe (nearest-point fallback otherwise), so a few neighbours of every probe are needed; that argues for `radius_m >= window_m`, not for all 341 077 points.
* Diagnostics (matching plots, footprint, transects) are drawn on the whole survey.

The cost, not the science, is what pushes toward a split (next section).

### Split for the final runs: `--stage calibrate` / `--stage map` (implemented)

Calibration only needs the probe-matched points; the maps need all points.

```bash
# 1. calibrate: EM points restricted to the probe neighbourhoods, FULL ensemble
#    (all alphas / forward models), Steps 0-5; writes stage_calibration.json; stops before Step 6
./run_one_scenario.sh -s real_single_base -c ensemble_scenarios_real.json --mode 2d --stage calibrate

# 2. map: all (or grid-thinned) points, ONLY the selected alpha / forward model / K
./run_one_scenario.sh -s real_single_base -c ensemble_scenarios_real.json --mode 2d --stage map \
    --calibration <output>/<scenario>_calibrate        # folder or stage_calibration.json
```

Use a scenario with no `em_subsample` (e.g. `real_single_base`) for both stages: `--stage calibrate` restricts the EM points to the probe neighbourhoods itself (radius 5 m unless the scenario sets `em_subsample.mode = "probes"` with its own radius), and `--stage map` then uses all points. A scenario that already thins with `mode = "probes"` (e.g. `real_single_test_probes`) would map only the probe neighbourhoods.

Each stage has its own run folder suffix and cache file. `--stage map` checks that depths0 / cond_ranges / epochs match the calibration before inverting anything, re-fits Steps 2-5 on the selected members and reports the drift against the calibration (`[WARN] CALIBRATION DRIFT` means: redo calibrate). `--stage map` cannot be combined with `--quick`.

**How `ws_localized_bandwidth_sweep` fits in.** The leave-one-probe-out CV only reads probe-matched points, so it runs in `--stage calibrate` only (on the full ensemble, against its rank-1 member). The chosen bandwidth is stored in `stage_calibration.json` (`localized_bandwidth`, `bandwidth_from_sweep`). In `--stage map` the sweep is skipped (logged as `[STAGE] map: ws_localized_bandwidth_sweep skipped`) and the stored bandwidth is reused as a fixed `ws_localized_bandwidth` for the kernel-localized fit, which is then evaluated at every map point (the kernel only needs probe data + target coordinates, so thinning the EM points does not change the fit, only where it is evaluated). Passing `--ws-localized-bandwidth C` to the map run overrides the stored value; the sweep list on the map CLI/scenario is ignored. Caveat: the localized fit is still a diagnostic sibling of Step 2 and does not feed Steps 3-6.

### Optional: calibrate Waxman-Smits by zone (future, clustering method to be discussed)

For real data it would be convenient to optionally cluster the field into zones and run one WS calibration per zone (instead of one set of parameters per horizon for the whole field). How to cluster is open. Candidates to discuss:

* **Geographic / management zones** (plots, crops, user-drawn polygons): simplest, easy to explain, needs a polygon file.
* **ECa-based clustering** (k-means / Gaussian mixture on time-mean ECa per coil, as in precision agriculture): data-driven, but circular, because the zones are defined by the same quantity that is then converted to theta.
* **Soil-map / texture-based** (external soil map, clay content): physically closest to what a, m and sigma_s represent.
* **Temporal-stability based** (zones with persistent ECa pattern across the 7 epochs).

**Possibly redundant with `ws_localized_bandwidth_sweep`.** The localized Step 2 fit (`run_petro_localized`) already lets the WS parameters vary in space: it fits a separate parameter set at every target location, weighting every TDR observation of the horizon by a Gaspari-Cohn kernel of its distance (`bandwidth -> inf` = the global per-horizon fit, `bandwidth -> 0` = nearest probe), and the bandwidth is chosen by leave-one-probe-out CV. Zones are the hard-partition version of the same idea. Where they differ:

* Localized fit: no clustering decision, one hyperparameter chosen by CV, smooth variation. But it only knows distance: it smooths across an abrupt soil boundary and cannot pool probes from two separate areas that share the same soil.
* Zones: can use a covariate (ECa, soil map, texture) so non-adjacent areas share parameters and sharp boundaries are respected, with more probes pooled per fit and parameters that are easy to interpret. But they add the clustering choice and need enough probes per zone.
* Both can be combined (kernel weights multiplied by a same-zone indicator, or a distance that includes the covariate), at the price of more complexity.

Suggested decision rule before building anything: look at what the bandwidth CV selects on the real data. If it picks a bandwidth much larger than the field, there is no spatial structure to exploit from 20 probes and zones are not worth it; if it picks a small one, there is structure, and zones are worth it only if a covariate or a boundary explains it that distance alone cannot. I have not seen that CV output for the real runs.

Things to settle with it: minimum number of TDR probes per zone (20 probes in total, so only a few zones; free parameters per zone must stay below what the probes can constrain); what a zone without a probe falls back to (global parameters or nearest zone); leave-one-probe-out CV must respect the zones; relation to the existing continuous alternatives (`ws_xy_variation`, localized Gaspari-Cohn fit `ws_localized_bandwidth_sweep`). Sketch: scenario field `ws_zones` (`null` | `{"method": "polygons"|"kmeans_eca"|"file", ...}`) producing a zone label per reference-grid point, and Steps 2/4 calibrating per (horizon, zone).

### Acceptance tests for the above

* A `grid` or `probes` run reproduces, at the probe-matched points, the optimal EC and theta of the full run (same `ec_optimal`, `theta_calc` within solver tolerance).
* Probe-to-EM matching report is unchanged (same matched indices/distances) or only gets closer.
* Cache fingerprint changes when `em_subsample` changes.
